# ТЗ и принятые решения

## Задача

Мини-игра-опрос на мероприятии молодёжного служения. Длительность активности
— около 15 минут, разовое использование (но проект остаётся).

Участники (ориентировочно 50 человек) заходят по ссылке с телефонов и
проходят ~15 вопросов, у каждого 4–6 вариантов ответа с картинками.
Оператор на ноутбуке, подключённом к проектору, в конце показывает залу
статистику по каждому вопросу.

## Сценарий

1. Люди сканируют QR / переходят по ссылке и попадают на заставку с афишей
   мероприятия. Заставка показывается всегда, при каждом заходе. Кнопка на
   ней говорит «Почати» новичку и «Продовжити» тому, кто уже начал, и во
   втором случае ведёт на первый неотвеченный вопрос.
2. Каждый идёт **в своём темпе** по всем вопросам, может вернуться назад и
   **изменить свой выбор**.
3. Пока идёт голосование, на проекторе — заставка. Ни вопросы, ни результаты
   на большой экран в это время не выводятся.
4. Когда все закончили, оператор открывает полноэкранный слайдер и листает
   статистику по вопросам вручную. Здесь зал и трансляция впервые видят
   и сами варианты, и распределение ответов.

## Принятые решения

### Без сборки, чистый HTML + JS

Рассматривался React + Vite. Отклонён: сборка тянет за собой деплой на
GitHub Pages с base path, костылём `404.html` и workflow в Actions — это
самый затратный и рискованный кусок работы, а выгоды для проекта такого
размера не даёт. Без сборки пуш в репозиторий = деплой.

### Firebase Firestore как бэкенд

Рассматривались Mock API сервисы (mockapi.io и подобные) — отклонены:
ключ в статике позволяет кому угодно стереть данные, нет серверной
агрегации. Рассматривались Supabase и Cloudflare Workers — отклонены как
незнакомые и требующие писать бэкенд.

Firestore выбран потому, что бэкенд писать не нужно вовсе: две функции
из браузера, живые подписки через `onSnapshot`, бесплатный тариф Spark
без привязки карты.

### Google Forms как альтернатива всему проекту

Рассматривалась всерьёз и признана рабочей для «просто получить цифры».
Отклонена ради зрелищности: нужен полноэкранный слайдер, картинки у
вариантов и живое обновление, чего форма не даёт.

### Документ на участника, а не на голос

```
sessions/{sessionId} → { q1: 'mountains', ... }
```

Причины:

1. Участник может **менять свой выбор** — это просто перезапись поля.
   При схеме «документ на голос» пришлось бы искать и удалять прежний.
2. Восстановление после перезагрузки телефона: `sessionId` в
   `localStorage`, человек возвращается к своим ответам.
3. Позволяет считать связи между ответами разных вопросов.
4. Нет конкуренции за запись: у Firestore лимит ~1 запись в секунду **на
   документ**, а здесь каждый пишет только в свой.

Минус, принятый осознанно: правила разрешают обновлять любой документ
сессии, то есть угадавший чужой случайный id может переписать чужие
ответы. Для 15-минутной активности несущественно.

### Админских прав нет вообще

Первоначально обсуждалась кнопка «закрыть голосование», которая требует
общего состояния в Firestore и, следовательно, ответа на вопрос «кто имеет
право её нажимать». От фичи отказались: оператор просто открывает слайдер
и показывает, что есть.

Как следствие — **ни одного поля, которое пишет оператор**. Он только
читает. Никакой авторизации, секретов в URL и правил с проверками.

Страница оператора не залинкована ниоткуда — этого достаточно.

### Отдельного экрана зала нет

Сначала предполагалась третья страница, показывающая залу текущие вопросы
во время голосования. От неё отказались: во время прохождения на проекторе
будет заставка, а вопросы и результаты зал видит одновременно — уже в
слайдере результатов.

Поэтому у оператора одна страница `host.html` и один режим слайдера:
результаты. Панель управления и слайдер живут в той же вкладке.

### Язык интерфейса — украинский

Весь текст, который видят участники и зал, — на украинском, зашит прямо в
разметку и в `questions.js`. Библиотека локализации не нужна: язык один и
второго не будет. Комментарии в коде и эта документация остаются как есть.

### Свой вариант ответа на каждом вопросе

Кроме карточек с картинками, у каждого вопроса есть поле «Свій варіант» —
свободный текст до 100 символов. Хранится как `qN: 'other'` плюс
`qN_text: '...'` в том же документе сессии.

Отдельной кнопки «Сохранить» у поля нет: текст записывается при переходе
к следующему вопросу, то есть кнопкой «Далі». Открытие поля сразу снимает
выбор с карточек — ответ может быть только один.

Выбор карточки после набранного текста стирает текст — и в интерфейсе, и в
базе (`qN_text` перезаписывается пустой строкой). Ответ всегда ровно один:
либо карточка, либо своя формулировка.

**Вопрос нельзя оставить без ответа.** Отсюда два правила. «Далі»
заблокирована, пока ответа нет вообще. А если человек открыл поле, ничего
не написал и ушёл — возвращается его прежний выбор, а не пустота: открытие
поля само по себе ответа не отменяет.

В статистику такие ответы **не входят**: проценты и полосы считаются только
по вариантам с картинками. На слайде результатов свободные ответы идут
отдельным блоком под полосами, текстом, с пометкой «поза статистикою» и их
количеством. Счётчик «відповіли» вверху слайда включает их — человек ведь
ответил.

Ограничение в 100 символов держит только клиент; правила Firestore его не
проверяют. Осознанный компромисс: правила не умеют дёшево валидировать
произвольный набор полей, а рисков на разовом мероприятии нет.

Текст участников выводится на экран оператора через `innerHTML`, поэтому
экранируется в `app/html.js`. Это единственное место в проекте, где
пользовательский ввод попадает в разметку.

### Кнопка «Очистить результаты» и право на удаление

На странице оператора внизу есть неброская кнопка, стирающая ответы всех
участников, с подтверждением в модалке. Нужна, чтобы прогнать игру начисто
после репетиции.

Авторизации в проекте нет, поэтому правило может разрешить удаление либо
всем, либо никому. Выбрано **всем** (`allow delete: if true`). Разобранные
альтернативы: анонимная авторизация с uid в правилах — надёжно, но добавляет
настройку и риск потерять доступ, если на мероприятии почистить браузер;
удаление через консоль Firebase — безопасно, но тогда кнопка на проде
бесполезна.

Принятый риск: тот, кто откроет исходники сайта, технически может стереть
ответы во время мероприятия. Активность длится 15 минут, страница оператора
нигде не залинкована, восстановление — переголосовать.

### Защита от вредоносного ввода

Свободный текст участника попадает на проектор, поэтому защита сделана в три
независимых слоя — каждый работает, даже если два других отказали:

1. **Очистка на входе** — `sanitizeText()` в `app/html.js` убирает угловые
   скобки, управляющие и невидимые символы (в том числе bidi-override, которым
   маскируют текст), схлопывает пробелы и режет до 100 символов.
2. **Текст как текст** — пользовательские строки попадают в DOM только через
   `textContent`, никогда не через `innerHTML`. Разметку из них собрать
   нельзя в принципе.
3. **Content-Security-Policy** — в `<head>` обеих страниц. `default-src
   'none'`, скрипты только свои и с `gstatic.com` (Firebase SDK), запросы
   только к Firestore. Инлайновые скрипты запрещены, поэтому даже успешная
   инъекция не выполнится.

Ради третьего слоя из кода убраны все инлайновые `onerror` и атрибуты
`style` — они бы требовали ослабить политику. Картинки прячутся при ошибке
через обработчик (`wireImageFallbacks`), ширина полос ставится из JS.

### Мобильный интерфейс — первичный

Практически все участники проходят опрос с телефонов, а слайдер результатов
попадает и в трансляцию. Поэтому вёрстка мобильная в первую очередь:
`dvh` вместо `vh`, отступ под системную полосу iPhone (`safe-area-inset`),
кнопки от 50 px по высоте, отдельные правила для узких экранов и для
телефона в горизонтальной ориентации. Слайдер на телефоне листается свайпом,
стрелки при этом уходят вниз, чтобы не отъедать ширину у полос.

### Вопросы хардкодом, без админки

Админка потребовала бы: вопросы в Firestore, редактор с формами, защиту
от посторонних и Firebase Storage для картинок — а Storage на новых
проектах требует платного тарифа Blaze. Правка массива в `questions.js`
для 15 вопросов удобнее любой формы.

### Картинка у каждого варианта, не у вопроса

Выбрано ради зрелищности: участник выбирает не слово, а изображение.
Требование к весу: 800–1000 px по ширине, WebP, до 100 КБ на файл.
Причина — гостевой Wi-Fi на полсотни телефонов, это главный реальный
риск производительности на мероприятии (не GitHub Pages и не Firestore).

## Нагрузка — расчёт

При 50 участниках и 15 вопросах:

- записей: до 750 при суточном лимите 20 000;
- чтений: порядка 1500 при лимите 50 000;
- хранилища: десятки килобайт при лимите 1 ГБ;
- трафик GitHub Pages: единицы мегабайт при лимите 100 ГБ в месяц.

Запас кратный. Узкое место — Wi-Fi в помещении.

## Явно вне скоупа

- Авторизация и роли.
- Принудительное закрытие голосования.
- Защита от накрутки (без авторизации невозможна в принципе;
  `localStorage` отсекает только случайный повтор).
- Таймеры, звук, имена участников, начисление очков.
- Защита самой кнопки очистки от посторонних — см. решение выше.
- Выгрузка результатов в CSV или таблицу — не нужна, результаты живут
  только на экране слайдера.
- Показ участникам чужих ответов на их телефонах.

## Порядок работ

1. Локально на моковых данных, итерации по внешнему виду. ← текущий этап
2. Подключение Firebase (создать web-app в консоли, вставить конфиг,
   опубликовать правила, `MOCK = false`), проверка с реального телефона.
3. Пустой публичный репозиторий на личном GitHub, пуш, включение Pages.
